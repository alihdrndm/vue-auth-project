# M0 — Repository audit and setup

## What was there

The repository started with the history of an old Vue 2/Firebase app. That app had already been removed, and the design export had been committed under `design/export/`. The audit found no backend, frontend scaffold, root scripts, Compose file, CI or docs. It also found four blockers in the local environment: `uv` was missing, Python 3.13 was missing (only 3.14 was installed), the Docker daemon was stopped, and the README and `.gitignore` were left over from the old app. Nothing was deleted or rewritten. Every change in this milestone is a new commit on top of the existing history.

## What was built

- **Backend skeleton** (`backend/`): a uv project on Python 3.13 and Django 6. Tooling is ruff, mypy strict with django-stubs, pytest with coverage, import-linter and Poe tasks.
- **API foundation** (`backend/src/eingang/`): `config.py` reads every setting once. `middleware.py` assigns request ids and writes the request log line. `problem.py` handles errors. `health.py` serves `/healthz` and `/readyz`. `temporal_client.py` holds the Temporal connection.
- **Frontend skeleton** (`frontend/`): Vue 3, Vite, TypeScript strict, ESLint, Prettier and Vitest. API types are generated from `backend/openapi.json`.
- **Root scripts** (`scripts/*.mjs`): `pnpm dev`, `verify`, `gen:api`, `test:e2e`, `seed` and `db:reset`, written as plain Node so they run the same on Windows, macOS and Linux.
- **Compose** (PostgreSQL 17 and the Temporal dev server), **CI**, and the first docs.

## Key decisions

1. **One error format, enforced in one place.** DRF exceptions go through `problem.exception_handler`. Errors that Django produces before a view runs go through `RequestContextMiddleware`, which rewrites them; examples are an unknown route, a disallowed host and a CSRF failure. The frontend can therefore always read `code`, `title` and `detail` and never has to parse HTML. The DRF handler plays the role an error interceptor plays in a JavaScript HTTP client: it maps exceptions to responses in one place.
2. **A synchronous Django view talking to an async SDK.** Temporal's Python client is `async`. Django views here are synchronous, like a plain Express handler that must not block on a promise without awaiting it. `temporal_client.py` runs one asyncio loop on a background thread per process and hands it work with `run_coroutine_threadsafe`. Each call has a timeout, so `/readyz` answers within its 2-second budget.
3. **Generated files must be identical on every OS.** `openapi.json` and `schema.d.ts` are committed, and CI fails if they are stale. `.gitattributes` enforces LF line endings, and the export tool writes LF explicitly, so a Windows checkout produces exactly the bytes Linux CI produces.

## Measured

- `pnpm verify`: all 9 steps pass. The backend has 35 tests at 93% coverage; the frontend has 1 test, and its build succeeds.
- `/readyz` returns 200 with the stack up. With PostgreSQL stopped it returns 503 `NOT_READY` naming the database, after 2.2 s. The Temporal UI on 8233 returns 200.

## Read first

`backend/src/eingang/config.py` → `middleware.py` → `problem.py` → `health.py`, then `scripts/verify.mjs`. Deviations from the specification are in `docs/DECISIONS.md`.
