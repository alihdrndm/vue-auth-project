# M2 — Validation, visualisation and the sample set

## What was built

- `tools/fetch_rules.py` downloads the pinned KoSIT releases (`v2026-01-31`): the validator configuration, the visualisation and the test suite. It checks every download against `vendor/rules.lock.json` and extracts only the files Eingang needs into `backend/vendor/`. Those files are committed, so tests and Docker builds never touch the network.
- `einvoice/validate.py` follows HANDOFF section 3. Step 1 is the XML Schema, which stops the run on failure. Step 2 is the EN 16931 Schematron. Step 3 is the XRechnung Schematron, for XRechnung 3.x only. `svrl.py` turns the SVRL report into issues. The result is `valid`, `warnings`, `invalid` or `not_applicable`.
- `einvoice/visualize.py` renders XML invoices with the official two-step KoSIT stylesheets as a static HTML page: English, no scripts, all sections visible.
- `tools/sample_data.py` and `tools/build_samples.py` generate the twelve fictional sandbox invoices: XRechnung UBL and CII, ZUGFeRD hybrids, a plain PDF and a scan. They also write `samples/manifest.json` and the precomputed detection, validation, invoice data, text and HTML that the M3/M4 seed loads without running any of this code.

## Key decisions

1. **Agree with the official validator, not just with the rules.** KoSIT's `scenarios.xml` raises or lowers individual rules per scenario, for example `BR-CL-23` to a warning or `CII-SR-452` to an error. `scenarios.py` reads those overrides, Saxon evaluates the scenarios' XPath 2.0 `match` expressions, and `validate.py` applies the overrides of the first matching scenario. The source of the validator itself confirms that Schematron is skipped after an XSD failure. All 86 KoSIT test-suite instances are strictly `valid`, and every corpus `fail` file is rejected or has a recorded reason.
2. **One thread owns SaxonC.** SaxonC runs in a native GraalVM runtime that belongs to the thread that created it. Calling it from the worker's other threads crashed it. So `saxon.py` hands every transformation to one dedicated thread, where the processor and the compiled stylesheets live. The idea is the same as a single Web Worker owning a WebAssembly instance while the page posts messages to it.
3. **Samples are data plus a builder plus proof.** The invoices are typed `CanonicalInvoice` objects, and the builder writes them through the M1 writer. The builder refuses to finish unless every sample detects and validates exactly as the sandbox table says: S05 fails with exactly `BR-DE-15`, and S04 is `not_applicable`. Building them showed that XRechnung needs BT-23 (business process), so the writer gained that option.

## Measured

- Validation of S01 after warm-up: 7–19 ms across runs (spec target: under 2 s). Compiling every stylesheet at worker start-up takes about 1 s.
- `pnpm verify` passes: 305 backend tests. `einvoice` covers 98.8% of lines and 96.7% of branches.
