# M3 — Models, sign-in, permissions and the first API

## What was built

- **Models** for every table in the "Database" section. Each has a UUID v7 key and an explicit plural table name. The custom `accounts.User` signs in with an email address and lives in the first migration, because it can never be swapped later. Events are append-only, and the LLM ledger survives a deleted organisation through a database-level `ON DELETE SET NULL`.
- **Sign-in and roles.** The SPA fetches a CSRF token, then signs in. Sessions last 12 hours; a sandbox session ends exactly when its sandbox expires (`401 SANDBOX_EXPIRED`). Each role rule of the endpoint table is one DRF permission class. Every query of organisation data goes through `accounts/scoping.py`, so another organisation's object is simply "not found".
- **Endpoints:**
  - `POST /sandbox` creates a demo organisation, its visitor and the two inactive sample people, and signs the visitor in.
  - `POST /documents` stores uploads and starts processing.
  - `GET /documents` lists them, with filters and orderings.
  - The document detail shows the invoice, checks, validation, approvals, events and `allowed_actions`.
  - Downloads, suppliers with their IBAN history, organisation settings, members, and the `create-org` command.
- **Rate limits.** 120 requests per minute per IP, 30 uploads per minute per user, 10 logins per minute per IP, and 5 sandboxes per hour per IP with 50 per day in total.

The action endpoints (review, approve, resolve, retry), exports, `/stats` and `/rules` come in M4 with the status machine and the workflows. `docs/DECISIONS.md` records why.

## Key decisions

1. **Limit an upload while it is read, not afterwards.** DRF's CSRF check reads the request body before any view runs, so a view cannot choose how the body is read. `UploadLimitMiddleware` refuses an oversized body from `Content-Length` alone and installs a reader that stops at the first byte past 4 MB. The type is decided by content only: PDF magic bytes, or a safe XML parse with a UBL/CII root and no DOCTYPE. A file name never decides anything. This is the backend counterpart of validating input before it reaches a component, not inside it.
2. **The server decides what a user may do; the UI only shows it.** `allowed_actions` lists every action of the document's status, enabled or not, with the first reason in the spec's order: role, sandbox, four-eyes, blocking checks. Each check carries the same kind of `resolve` state. The Vue app renders these states and never re-implements permissions, much like a JavaScript client that trusts the server's feature flags rather than computing them.
3. **Prove isolation, don't assume it.** `tests/test_idor.py` calls every object endpoint as an admin of one organisation with the ids of another's objects, and checks the answer is 404 and nothing changed. A guard test fails when someone adds an object route without adding it to the list. `tests/test_error_codes.py` checks every endpoint against 401, 403, 405 and the rate limits, and that every error code the code uses is documented.

## Measured

- `pnpm verify` passes with 577 backend tests. Coverage per package is between 94% and 99% of lines.
- A smoke test against the running server worked end to end: CSRF, login, upload of sample S01, then the list.
