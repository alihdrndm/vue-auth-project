# M4 — Workflows, checks, review and the sandbox seed

## What was built

- **`ProcessInvoiceWorkflow`** runs one document from detection to a decision. It detects the document, validates and parses the XML, renders the visualisation, matches the supplier, runs the checks, then waits for people. While an invoice awaits approval, a durable timer sends up to three reminders. The workflow ends on export, on delete, or after 180 days of waiting. The LLM steps (extraction, the PDF-versus-XML comparison, rule explanations) are refused as "disabled" until M5. The workflow then records check C12 or the note "Visible PDF not compared" and carries on.
- **The status machine** (`invoices/status.py`) is the only code that changes a document's status. It checks the role, the condition (blocking checks, four-eyes, comment length) and writes the event.
- **Checks C01–C16** and **supplier matching** with an IBAN history. Resolving C05 confirms the new IBAN.
- **Review endpoints:** edit fields, resolve a check, mark reviewed, decide, send back, reopen, retry. They also cover exports (German CSV, ZIP bundle), `/stats` and `/rules/{id}`.
- **`MaintenanceWorkflow`** runs daily at 03:10 UTC. It deletes expired sandboxes, starts uploads that never started, re-signals workflows whose phase disagrees with the database, and logs counts. It also creates the schedules with `ensure_schedules` and handles the optional IMAP intake (`MailboxPollWorkflow`).
- **The sandbox seed:** every new sandbox, `pnpm seed` and the e2e setup get the twelve samples in their documented state, with no LLM call and no workflow.

## Key decisions

1. **The database is the truth; signals only wake.** The API commits a transition, then signals the workflow. Every signal just wakes the waiting loop, which re-reads the status through an activity. A lost or duplicated signal therefore cannot corrupt anything, and the daily maintenance repairs a missed one. In frontend terms, a signal is like an event telling a component to refetch, not a payload it trusts.
2. **Workflows are pure orchestration.** Workflow modules import only the standard library, `temporalio` and `contracts.py`, and call activities by name. Temporal replays workflow code, so it must be deterministic; all I/O lives in activities, and an import-linter contract enforces the split. Tests run the workflows in Temporal's time-skipping environment, so "three reminders over fifteen days" runs in milliseconds.
3. **The seed reuses the real pipeline's functions.** It takes the precomputed detection, validation and invoice of each sample, then runs the same supplier matching, checks and status rule as the activities (`invoices/persist.py` is shared). A test asserts each sample's checks and status against `samples/manifest.json`. The seed never imports validation or PDF code, so the API process stays light.

## Measured

- `pnpm verify` passes with 1250 backend tests. Coverage per package is between 95.5% and 99.1% of lines.
- Live: sample S01, uploaded through the running API with the worker and Temporal, reached `awaiting_approval` in 2.7 s (target 10 s). It had only C04 and a valid validation report.
